### P4 怎么写：先定瓶颈，再定装配，最后定初始化

**要点**
- 写作顺序不是"从第一行往下写"，而是自顶向下拆三层。
- 第一步定 block 形状：1×1 降维 → 3×3 → 1×1 升维，3×3 只在 64 通道上做，参数压到 20%。
- 第二步定装配规则：stride 放 conv2（v1.5 布局）；`expansion = 4` 必须是类属性；三级委托 `ResNet → _make_layer → block`；四层配置 64×3 / 128×4 / 256×6 / 512×3。
- 第三步补初始化：53 个卷积 kaiming `fan_out`，53 个 BN 置 1/0，`fc` 不初始化。
- 代码里三个注释点是三个陷阱：判据用 `or`、stride 与 downsample 只给首块、`inplanes` 更新时序。

**口播**
> 这页讲"怎么把它写出来"。我的写法不是从第一行往下写，是自顶向下拆三层：先定 block 的形状，再定装配规则，最后补初始化。
>
> 第一层，block 的形状。1×1 降维、3×3、1×1 升维。同样是 256 通道进、256 通道出，直接做 3×3 要 58 万参数；Bottleneck 先降到 64，3×3 在 64 通道上做完再升回 256，只要 11.8 万，五分之一。所以它的本质是"让贵的 3×3 在窄通道上做"。
>
> 第二层，装配规则。三个点：stride 放在中间那个 3×3 上，这是 v1.5 布局；`expansion = 4` 必须是类属性，因为 `_make_layer` 要在实例之外用它算输出通道；装配是三级委托，`ResNet` 交给 `_make_layer`，`_make_layer` 交给 block，超参只在一处声明。
>
> 第三层，初始化。53 个卷积用 kaiming `fan_out`，53 个 BN 置 1 和 0，`fc` 不初始化 —— 这点和很多人的直觉相反，torchvision 确实没有初始化全连接层。
>
> 下面这段 `_make_layer` 里有三个注释点，都是我自己踩过的：判据必须用 `or` 不是 `and`；stride 和 downsample 只传给第一个 block；`inplanes` 的更新必须放在首块之后、循环之前。

**追问**
- *问：为什么 v1.5 把 stride 挪到 3×3？* → 1×1 卷积做下采样会丢掉 3/4 的信息（只取一个点），3×3 卷积下采样是带邻域信息的加权，精度更好。
- *问：`expansion` 写进 `__init__` 会怎样？* → `_make_layer` 在构造 block 之前就要知道输出通道，此时还没有实例，直接 `AttributeError` 或算错。
- *问：为什么 `fc` 不初始化？* → torchvision 原实现就没有，为了和官方权重、官方训练行为保持完全一致。

### P5 怎么验收：四重等价，逐级加严

**要点**
- 四关：结构（320 个键名与形状）、规模（参数量）、初始化（kaiming + BN）、行为（逐位输出）。
- 关键数字：1000 类 25,557,032；100 类 23,712,932；行为关最大绝对差 **0.0e+00**。
- 为什么四关：前两关只看"形状对不对"，两个真实错误在 state_dict 层面完全隐形。

**口播**
> 写完之后怎么验收？我的标准不是"能跑通"，是"和 torchvision 逐位比对"。
>
> 四关，逐级加严。第一关结构：320 个 state_dict 的键名和形状全部一致。第二关规模：参数量精确相等，1000 类是 25,557,032。第三关初始化：53 个卷积逐个校验 kaiming_normal 的标准差，53 个 BN 的权重是 1、偏置是 0。
>
> 第四关最硬：载入官方权重，把 layer1 到 layer4 每一层的输出都取出来比，最大绝对差是 0 —— 不是"很小"，是逐位相同。
>
> 为什么要四关而不是两关？因为前两关只看形状。BatchNorm1d 代替 BatchNorm2d、1×1 卷积误加 padding，这两个错误在 state_dict 层面完全看不出来 —— 键名对、形状对、参数量对，只有跑到前向才炸。下一页就是这两个。

**追问**
- *问：为什么能到 0 而不是 1e-7？* → 同一套权重、同样的算子顺序、同样的 fp32 累加顺序，PyTorch 的 CPU 卷积是确定性的，所以逐位相同。如果中间做过 cast 或用了不同 kernel 就会差 1e-6 量级。
- *问：四关各自能证伪什么？* → 结构抓"少一个模块/多一个模块"；规模抓"通道数配错"；初始化抓"忘了调 `_init_weights`"；行为抓"顺序错/维度错"。

### P6 验收为什么必须分层：四个坑，四种发现方式

**要点**
- 坑 1 BatchNorm1d、坑 2 1×1 带 padding：**只有前向能抓**。
- 坑 3 downsample 被丢弃：只有结构测试能抓（少 12 个键）。
- 坑 4 手写 backward：概念错误，`nn.Module` 没有 `.backward()`。
- 结论：验收清单要分四层，是因为每个坑都只有某一层能抓到。

**口播**
> 这四个坑是按"谁发现的"来排的，因为这直接说明测试该写在哪一层。
>
> 前两个只有前向能抓。BatchNorm1d 那个，键名、形状、参数量全部正常，一跑前向就 `ValueError: expected 2D or 3D input`。1×1 卷积加 padding 更阴 —— 权重形状完全不变，但 56×56 变成 58×58，等到与旁路相加时才发现尺寸对不上。
>
> 第三个，downsample 参数收到了但忘了存成 `self.downsample`，这个 forward 里看不出来（旁路直接不加），只有结构测试能抓 —— 少 12 个键。
>
> 第四个是我最开始的误解：给 Bottleneck 手写了一个 `backward`。`nn.Module` 根本没有 `.backward()` 这个方法，autograd 全自动。这个只有人看代码能发现。
>
> 所以"12 项全绿"不等于"什么错都抓得住"。每类测试都要有代表用例。

### P8 为什么选 YOLO11 与 YOLO26

**要点**
- 「改动」优于「演进」：v5→v11 跨 6 代，只能对上结果；11→26 只有 6 处改动，每行 YAML 能定位到论文某条。
- 三个方向都有代表：结构 / 后处理 / 优化器。
- 结论可被实测检验：两代都有 fused 权重，同一套脚本能跑 A/B。

**口播**
> 为什么选这两个版本。如果读 v5 到 v11，中间跨了六代，读完只能对上"结果变了"，对不上"过程怎么变的"。11 到 26 只有六处结构性改动，每行 YAML 都能定位到论文的某一条。
>
> 而且这六处正好覆盖三个方向：结构上的颈部和 SPPF、后处理上的去 DFL 和双头、优化器上的 SGD 换 MuSGD。一次精读把三类改动都覆盖了。
>
> 右边是官方性能表。注意 26n 在 T4 上反而更慢（1.7 vs 1.5），但 CPU 上快很多（38.9 vs 56.1）。这个反差是后面实测要解释的。

### P9 六处改动，一条因果链

**要点**
- 六条：o2o 头 / Progressive / 去 DFL / STAL / MuSGD / 颈部加注意力。
- 前四条是"换"，后两条是"加"。
- 因果链：端侧不想跑 NMS → 训 o2o 头 → 难训 → Progressive → 顺手去 DFL → 小目标靠 STAL → 训练慢靠 MuSGD。

**口播**
> 这是全局地图，后面每一页对应这里的一行。
>
> 读这六条的关键是看因果链，不是看清单。起点是一个业务诉求：端侧不想跑 NMS。要省掉 NMS，就必须在训练时训出一个一对一的头，也就是 o2o 头。
>
> 但 o2o 头早期正样本太少，训不动，于是加了 Progressive —— 先主要靠一对多学，再逐步把权重交接到一对一的头上。
>
> 顺手把 DFL 去掉了，头从 144 通道降到 84 通道，代价是掉 0.6 个点。小目标的零指派问题靠 STAL 救回来。训练变慢就上 MuSGD。
>
> 所以前四条是"换"——换头、换指派、换回归、换调度；后两条是"加"——加注意力、换优化器。

**追问**
- *问：为什么去掉 DFL 掉点还能接受？* → 论文给的账是 −0.6 AP，但省下 60 个通道的计算，端侧延迟收益更大；后面 STAL +0.2、颈部 +0.2 补回一部分。

### P11 结构改动怎么落到代码：SPPF 加残差 + 颈部换模块

**要点**
- SPPF：`[1024, 5]` → `[1024, 5, 3, True]`，第 4 个参数 `shortcut=True` 给模块加了一条直连。
- 颈部：P5 行 `C3k×2` → `C3k2`（repeats 2→1），颈三层 `attn=False→True`，在 C3k2 后接 PSABlock。
- 实测两个尺度方向相反：n/s 参数 +27%、GFLOPs +51%；l/x 参数 −23%、GFLOPs −17%。
- 原因：26 写死 repeats=1，永远不受 depth 缩放影响。

**口播**
> YAML 上那六行，真正动到 Python 实现的其实只有两处。
>
> 第一处，SPPF。原来是 `[1024, 5]`，26 变成 `[1024, 5, 3, True]`，第四个参数是 shortcut，等于把这个模块的主干输出和三级池化融合结果相加，加了一条直连。这就是论文里说的"给 SPPF 加残差"。
>
> 第二处，颈部。P5 那一行原来是两个 C3k，现在变成一个 C3k2，repeats 从 2 降到 1；同时颈部三层的 attn 从 False 变 True，也就是在 C3k2 后面接一个 PSABlock。
>
> 有意思的是这个改动的实测效果在两个尺度上方向相反：n 和 s 变重了，参数多 27%、GFLOPs 多 51%；l 和 x 反而变轻，参数少 23%、GFLOPs 少 17%。
>
> 原因是 11 的 repeats=2 会被 depth 缩放放大成两个 C3k，而 26 写死 repeats=1，永远不受缩放影响。所以不能拿 n 尺度的结论去推 l/x 尺度。

**追问**
- *问：那 26 到底是不是更轻？* → 看尺度。官方给的表格是 n/s/m 变重、l/x 变轻，而厂商主推 n 和 s，所以对外宣传里"更轻"要打折扣。

### P12 检测头：四个开关决定输出的形状

**要点**
- ① `no = nc + reg_max×4`：11 是 144，26 是 84，少 60 通道。
- ② cv3 两种写法：legacy 决定普通 Conv 还是 DWConv。
- ③ dfl 条件模块：reg_max=1 时就是 `nn.Identity()`。
- ④ deepcopy 出第二支，初始权重逐位相同。

**口播**
> 检测头是这次改动最集中的地方，但 `Detect.__init__` 一共只有四个分支。
>
> 第一个，`no`。它既是输出通道数，也是最后那层卷积的核数。11 是 80 类加 16 个 bin 乘 4 等于 144；26 是 80 加 4 等于 84。少的不只是 60 个数 —— 框支里 5 个卷积的输入通道全从 64 降到 4，所以实测框支从 13.17 毫秒掉到 3.17 毫秒。
>
> 第二个，cv3 有两种写法，看 legacy：用普通 3×3，或者用 DWConv 版。
>
> 第三个，dfl 是条件模块，reg_max 大于 1 才建；26 的 reg_max 是 1，所以 dfl 就是 Identity，整条 DFL 分支在结构上直接消失。
>
> 第四个，deepcopy 复制出第二支，`one2one_cv2/cv3` 和 `cv2/cv3` 初始权重逐位相同。这一条很重要：它保证了训练第 0 步时两支输出完全一样，后面的 Progressive 权重调度才有意义。

**追问**
- *问：为什么两支必须同初始权重？* → 否则前期 o2o 学到的不是"同一批锚点的更严格版本"，而是另一个噪声源。

### P14 Detect.forward：eval 时两支都会算

**要点**
- o2m 无条件先算；有 o2o 再算一遍，训练时输入先 `detach`。
- training 返回两支；eval 只走一支。
- 🧪 未 fuse 时 26n 比 11n 慢 16%（44.0–45.3 vs 38.0–38.6 ms），fuse 后打平。

**口播**
> 这页是最容易读出"性能 bug"的一页。
>
> 第一行：o2m 那一支是无条件算的，不管训练还是推理。
>
> 第二行：如果模型有 o2o 那一支，就再算一遍，但输入是 detach 过的。注意后面那个 `if self.training else x` —— 只有训练才 detach，因为推理本来就不建图。这样 o2o 的梯度不会回传到 neck。
>
> 然后 `if self.training: return preds`，训练时两支都返回、都要梯度；否则只走 `_inference`，按 end2end 选一支。
>
> 问题就在这儿：eval 的时候两支都算完了，只丢一支。所以未 fuse 的 26n 比 11n 慢 16%，fuse 之后才打平。这就是为什么我所有基准的第一条纪律都是必须先 fuse。

**追问**
- *问：为什么 o2o 要 detach？* → 让两支各自负责一段特征，避免 o2o 的梯度反过来改写 neck；同时也让 o2o 变成一个"冻结特征上的更严格指派"。

### P15 形状流：(1,84,8400) → (1,300,6)

**要点**
- 8400 = 6400 + 1600 + 400，是三段拼接出来的。
- 顺序约束：`make_anchors` 必须同序，否则 topk 索引指向错坐标。
- 这种 bug 形状检查发现不了，只能靠数值或可视化。

**口播**
> 这条前向的形状我单独拿一页，因为 8400 这个数最容易让人困惑。
>
> 它不是一张图，是三张图拼的：P3 是 80×80 等于 6400，P4 是 40×40 等于 1600，P5 是 20×20 等于 400，加起来 8400。
>
> 所以有一条顺序约束：`make_anchors` 必须按同样的顺序生成锚点。顺序错了，topk 拿到的索引会指向另一层的坐标，框就出现在错误的位置。
>
> 而且这种 bug 形状检查完全发现不了 —— 输入 (1,84,8400)、输出 (1,300,6)，一个维度都不差。只有数值会错，只能靠可视化或者已知答案比对。这也是我为什么强调"验收要看数值不只看形状"。

**追问**
- *问：8400 会随输入尺寸变吗？* → 会。640×640 才是 8400；换分辨率这三个数一起变，所以任何硬编码 8400 的代码都是隐患。

### P16 两段 topk 与两层 fuse()

**要点**
- 300 个框分两段：8400 锚点 → 300 锚点 → 300 个（锚点, 类）对。
- 第二段是 multi-label：同一个锚点可以被当成多个类输出。
- fuse 有两层：模型级折 BN，头级只选支，一行 BN 都不碰。
- ⚠ `groups` 不是「第二段」，它是导出到 engine 时的分组加速，PyTorch 推理时 groups=1。

**口播**
> 两个容易混淆的点。
>
> 第一个，300 个框是怎么挑出来的。不是一次 topk，是两段。第一段先从 8400 个锚点里、按每个锚点的最高类分，取 300 个锚点。第二段把这 300 个锚点的完整分数收回来，是 300 乘 80、也就是 24000 个"锚点类"对，再从中取 300 个。所以第二段的意义是 multi-label —— 同一个锚点可以被当成多个类输出。
>
> 这里我要特别说明一处我自己笔记里的错误：`_grouped_topk` 的第二个、第三个参数是 k 和 groups，不是"5 乘 5"那种写法。`groups` 只有在导出到 engine 时才变成 8 组做分组加速，PyTorch 推理时是 1，也就是普通 topk。我一开始按分组理解，写出来跟源码对不上，回头看源码才改对。
>
> 第二个，fuse 有两层。模型级的 `BaseModel.fuse()` 负责把 BN 折进卷积，然后对每个 Detect 调 `m.fuse()`；头级的 `Detect.fuse()` 只做选支 —— 靠 `setattr(name, None)` 把不用的那一支置空，一行 BN 都不碰。所以单独调 `Detect.fuse()` 对 BN 毫无作用。
>
> 实测账：26n 参数从 257 万降到 240 万，少的 163,348 正好是 o2o 那一支；head 内 BN 从 36 变成 0。11n 只减 7,832，因为它没有第二支，减掉的只是 BN 参数。

**追问**
- *问：fuse 之后还能训练吗？* → 不能。选支把一支置成 None 了，是不可逆的推理专用变换。

### P17 端到端后处理：nms 是三态，不是开关

**要点**
- `None`（默认）/ `True` 都走 o2m + NMS；只有 `False` 走 o2o、输出 (1,300,6)。
- 端到端分支只做 conf 过滤 → 类别过滤 → max_det 截断，没有 IoU 抑制。
- `iou_thres` / `agnostic_nms` / `multi_label` 在这条路上全部失效。
- 🧪 NMS 单独 180.5 ms，但那是最坏情况（conf=0.001）。

**口播**
> nms 这个参数是三态，不是布尔开关，这点很容易记错。
>
> 默认 None，还有 True，两者推理行为一样：走 o2m 那一支，再跑 NMS；区别只在导出时是否把 NMS 嵌进图。只有显式设成 False，才走 o2o、没有任何抑制，直接输出 300 行 6 列的张量。
>
> 端到端这条分支只做三件事：按 conf 过滤、按类别过滤、按 max_det 截断。没有 IoU 抑制。所以 `iou_thres`、`agnostic_nms`、`multi_label` 在这条路上全部失效 —— 调它们不会有任何效果，排查问题的时候容易误判。
>
> 再说成本。NMS 单独测是 180.5 毫秒，而同样条件下前向只要 33 毫秒左右。但要注意这是 conf=0.001 的极端设置，几乎所有候选都进了 NMS，是最坏情况；真实推理用 0.25。所以"省了 180 毫秒"这句话是错的。

**追问**
- *问：那端到端到底省多少？* → 在真实 conf 下省的是"随候选数增长的那部分"，不是固定的 180 ms；官方给的 CPU 数字 26n 38.9 ms 已经是端到端口径。

### P18 损失与指派：TAL 五步的骨架一步没变

**要点**
- 五步：候选筛选 → 对齐指标 → 每 GT 取 topk → 冲突消解 → 软目标。
- 26 只动了头尾：第一步换 STAL，另加 E2ELoss 给两支加权。
- `target_scores_sum` = Σ norm_align，让 loss 与目标数量无关。

**口播**
> 损失这块，先把骨架交代清楚：TAL 五步，候选筛选、算对齐指标、每个 GT 取 topk、冲突消解、生成软目标。
>
> 26 的三条改动全在头尾：第一步换成 STAL，另外新增 E2ELoss 给两支加权。中间三步 —— 对齐指标的指数、topk 的 k 值、冲突消解的规则 —— 全部沿用 11。所以"26 改了指派"这句话要说得更准确一点：它改的是边界条件，不是骨架。
>
> 还有个小细节值得说：`target_scores_sum` 是软对齐分数之和，它让 loss 与目标数量无关 —— 1 个目标和 100 个目标的 loss 量级不会差 100 倍，同时 box 和 cls 的量纲才可比。

### P19 STAL 与 IoU^6：一个放大 GT，一个放大差异

**要点**
- `IoU^6`：0.5→0.0156、0.9→0.5310，差 34 倍（线性只差 1.8 倍）。
- `cls^0.5` 反过来把分类分压平。
- STAL：`s_ref=16`，GT 边长 <16px 时撑到 16×16 再判候选，原始框不变。
- ⚠ 放大的是 GT，不是预测量。

**口播**
> 这两个点经常被讲反，我单独拆一页。
>
> 先看 `IoU^6`。IoU 0.5 的六次方是 0.0156，0.9 的六次方是 0.531，差 34 倍；如果按线性算只差 1.8 倍。所以这个六次方把"框准"的差异放大了大约 19 倍，让定位质量主导正样本的选择。
>
> 反过来，分类分是开根号，0.9 变成 0.95、0.1 变成 0.32 —— 把差距压平，不让高置信度的类压过框质量。两个指数一升一降，是配套设计的。
>
> 再看 STAL。它只改第一步候选筛选：`s_ref` 是 16、也就是下一级的 stride，GT 边长小于 16 像素的时候先把 GT 撑到 16×16 再判候选；原始框保持不变，仍然用于匹配和回归。效果是 +0.2 AP，小目标 AP 从 29.0 到 29.6。
>
> ⚠ 这里必须说准：放大的是 GT，不是预测量。很多笔记写成"预测量被放大"，那是错的。

**追问**
- *问：为什么要撑到 16×16？* → 小于 16px 的目标，能落进它内部的锚点中心太少，候选集会接近空；撑一下保证每个小目标至少有一批候选。

### P20 E2ELoss：给两支做权重调度

**要点**
- 不是固定 0.5/0.5：o2m 0.8→0.1、o2o 0.2→0.9，按 epoch 线性过渡。
- 初始值 0.8、终局 0.1，斜率 0.7。
- ⚠ 训练日志来自 o2o 单支，且 box 从 DFL 改成 L1，不能与 YOLO11 曲线直接比。

**口播**
> E2ELoss 是把两支的 loss 加权，但不是固定的 0.5 比 0.5。
>
> 初始是 o2m 0.8、o2o 0.2，终局反过来 o2m 0.1、o2o 0.9，中间按 epoch 线性过渡。手算一下：训练 100 个 epoch 的话，第 1 个 epoch 是 0.793 和 0.207，第 50 个是 0.446 和 0.554，第 99 个是 0.1 和 0.9。等于说前期先让 o2m 把模型带起来，后期把话语权交给 o2o。
>
> 这一页有个坑必须提醒：训练日志里那个字典，取的是 o2o 单支的 loss。而且 box 已经从 DFL 改成 L1 了，所以指标名字虽然一样，含义不同 —— 不能拿 26 的训练曲线去和 11 的曲线直接比。

**追问**
- *问：为什么前期要靠 o2m？* → o2m 是密集监督，收敛快；一上来就用 o2o 的稀疏指派，早期正样本太少，训不动。

### P21 MuSGD：同一份参数在一个 step 里更新两次

**要点**
- 多维参数先 Muon 正交化更新一次，再走一遍 SGD。
- 手算：`p ← p − 0.002·O − 0.019·g`，两份梯度、两个步长。
- 1D 参数（BN、bias）只走纯 SGD。

**口播**
> MuSGD 这个名字容易误解成"Muon 和 SGD 二选一"，其实是同一份参数在一个 step 里更新两次。
>
> 手算一遍最清楚。假设学习率 0.01、β 0.9、muon 权重 0.2、sgd 权重 1.0，初始动量都是 0。
>
> 第一步算 Muon 的动量，得到 0.1 倍梯度；第二步算出更新方向是 0.19 倍梯度；第三步做正交化，让奇异值接近 1；第四步按 0.01 乘 0.2 的步长更新一次，也就是 −0.002 乘 O。
>
> 然后进入 SGD 那一半：动量变成 g，nesterov 更新量是 1.9 倍 g；第五步再按 0.01 更新一次，−0.019 乘 g。
>
> 最后合起来：参数减去 0.002 乘 O，再减去 0.019 乘 g。所以是一次 step 里两次更新、两份梯度、两个步长 —— 不是加权平均。
>
> 另外 1D 参数，也就是 BN 和 bias，只走纯 SGD，不走 Muon，因为正交化对向量没有意义。

**追问**
- *问：那它比 SGD 快在哪？* → 论文给的对比是 500 epoch 47.4 对 SGD 600 epoch 47.0，省 100 个 epoch；但每步慢约 2 倍，净收益要看总时间。

### P22 几个容易读漏的地方：尺度不变性、权重、怎么被选中

**要点**
- Muon 那半步长与梯度幅度解耦：梯度 ×1000，输出几乎不变（1.350047 vs 1.350006）。
- 发布权重 0.53/0.67 ≠ 代码默认 0.2/1.0，也不是和为 1 的凸混合。
- `optimizer=auto`：`iterations > 10000` 才选 MuSGD，否则 AdamW。
- 三层数值保险：clip_grad_norm(10.0) → AMP 跳过 step → 回滚 last.pt。

**口播**
> 这几条都是读代码时才发现的，论文里没有。
>
> 第一，尺度不变性。`muon_update` 先做 Frobenius 归一化，再做 5 次 Newton–Schulz，系数是 3.4445、−4.7750、2.0315，输出只由形状决定。实测梯度乘 1000，输出是 1.350047 对 1.350006，差 3.6 个 1e-4、来自 bf16。含义是 Muon 那半步长等于学习率乘 muon 权重，和梯度幅度解耦 —— 梯度幅度的信息只由 SGD 那半传递。
>
> 第二，权重对不上。论文 Table S7 给的发布 checkpoint 是 0.53 和 0.67，Table S4 的预训练 checkpoint 是 0.45 和 0.55，而代码里 `trainer.py:1220` 的默认值是 0.2 和 1.0。而且 0.53 加 0.67 等于 1.20，不是和为 1 的凸混合 —— 说明这是两个独立的步长系数，发布权重不是用当前代码默认值训出来的。
>
> 第三，怎么被选中。`optimizer=auto` 的规则是：迭代次数超过一万才选 MuSGD、学习率 0.01，否则用 AdamW。所以小数据集根本触发不了 MuSGD —— 这条直接解释了"为什么我跑小实验看不到 MuSGD 的效果"。
>
> 最后是三层数值保险：梯度裁剪写死 10.0、AMP 遇到 inf 跳过这一步、NaN 恢复会回滚 last.pt，最多 3 次。

**追问**
- *问：那 MuSGD 我该怎么用？* → 要么把迭代数撑过一万，要么显式指定优化器；默认 auto 在小实验里不会选中它。

### P23 实测①：线程扩展

**要点**
- 四条结论：吃满核 / 递减 / 地板 / 26 的优势看运行时。
- 并行核数 0.99/2.04/4.13/7.91/11.73/14.75，利用率 ≈ 线程数/16。
- 12→16 线程 **0.97×，回退**。
- torch 下 26 只在 ≤6 线程领先（1T 是 11 的 91.9%）；ORT 下全程快 10–14%。

**口播**
> 这页开始是实测。协议先说清楚：640 输入、fuse 之后、`inference_mode`、30 次取中位数报 p95，不报最小值；两个运行时在同一进程里交错 A/B。
>
> 四条结论。第一，给多少核就吃多少核，并行核数从 0.99 一路到 14.75，整机利用率基本就是线程数除以 16。
>
> 第二，收益掉得很快：1 到 4 线程还有 2.32 倍，4 到 8 只剩 1.13 倍，8 到 12 是 1.09 倍，12 到 16 反而回退到 0.97 倍。并行效率从 58% 掉到 24%。
>
> 第三，地板：torch 12 线程 32.6 毫秒，ORT 23.3 毫秒。
>
> 第四条最关键：26 的优势完全取决于运行时。在 torch 下，26 只在 6 线程以下领先，1 线程时是 11 的 91.9%；8 线程以上反被 11 超过 2 到 3 个点。但在 ORT 下全程快 10 到 14%。
>
> 工程建议：线程别设成逻辑核数，4 到 8 是性价比拐点。

**追问**
- *问：为什么 16 线程反而慢？* → 超线程争抢执行单元 + 降频；数据上并行核数虽然到 14.75，但单核效率已经掉到 24%。
- *问：为什么 torch 下 8 线程以上 26 反而慢？* → 见 P15：PSA 注意力的扩展性差，C3k2 的 1→16 线程缩放只有 2.23×，而 11 是 2.60×。

### P24 实测②：模块耗时

**要点**
- 26 省下的几乎全在框支：`cv2` 13.17 → 3.17 ms，分类支几乎不变（7.97 vs 7.51）。
- 根因：`reg_max × 4`，64 通道 vs 4 通道。
- 谁最吃核：Concat 1.45–1.56× < head 1.72× < C2PSA 1.85–2.02× < C3k2 2.23–2.60× < Conv 4.05× ≈ SPPF 4.60×。
- ⚠️ 模块表不能和 ORT 延迟相加：eager 单次前向 1226/1442 次 aten 调用，ORT 图只有 431/496 个节点。

**口播**
> 上一页说 26 在 ORT 下快 10 到 14%，这页回答"省在哪"。方法是对每个顶层模块挂 forward hook。
>
> 结论很集中：省下的几乎全在框支。26n 的框支 `cv2` 从 13.17 毫秒降到 3.17 毫秒，而分类支几乎没变，7.97 对 7.51。为什么？因为框支的输出通道是 `reg_max × 4`，11 是 64 通道，26 只有 4 通道。
>
> 右边第二点解释上一页的反差：注意力模块在多核上扩展性差。Concat 能到 1.5 倍，Conv 和 SPPF 能到 4 倍，但 PSA 只有 1.85 到 2.02 倍，C3k2 在 26 上也从 11 的 2.60 倍掉到 2.23 倍。这就是为什么核一多，26 的优势就被吃掉了。
>
> 最后一句要强调：这张模块表不能和 ORT 的延迟相加或对比。模块表是 PyTorch eager，单次前向有 1226 次 aten 调用；ORT 的图只有 431 个节点，还做了算子融合。

### P25 实测③：内存

**要点**
- 线程 1→16 只涨约 2%（1.2–1.4 MB/线程）。
- 固定开销：torch 235–244 MB，ORT 370–379 MB；权重只有 9–10 MB。
- commit ≫ WS：torch 792–815 vs 275–282；ORT 1004–1018 vs 445–460。
- 规划：按 commit 计，单进程预留 0.8–1.0 GB。

**口播**
> 内存这页的结论反直觉：线程数几乎不影响内存。从 1 线程到 16 线程总共只涨 2%，每个线程一两兆。
>
> 真正的大头是固定开销：torch 235 到 244 兆，ORT 370 到 379 兆，而模型权重本身只有 9 到 10 兆。所以"模型小就能省内存"是错的。
>
> 还有一个必须分清的：Working Set 和 Commit。commit 基本是 Working Set 的 2 到 3 倍。如果是内存受限的部署环境，要按 commit 算，单进程预留 0.8 到 1.0 GB。

### P26 口径审查与方法沉淀

**要点**
- 可信的：fuse 的影响（25%）、1 线程下 26 更快（6–12%）、ORT 下 26 更快（7–14%）。
- 不可信的：8 线程下 26 vs 11（1–3%）、DFL 省 1%。
- 官方 vs 我们：同线程归一后官方快 1.94×（11n）/ 1.54×（26n），11n 多出的 25% 说明老图 DFL 子图没被融合。
- 三条方法：口径先行、比值优于绝对值、>10% 才作结论。

**口播**
> 这页是我觉得这周最有价值的一页 —— 不是结论，是"哪些结论能信"。
>
> 同一份代码、同一台机器，8 线程的延迟跨会话会漂移 10% 左右。所以 1 到 3 个点的差异，在这台机器上是不可分辨的，报出来就是噪声。DFL 只省 1%，必须用 ORT 加 1 线程才测得出 —— 这解释了为什么光看总延迟会觉得"DFL 去掉了怎么没变快"。
>
> 和官方数字对账：官方 CPU 是 11n 56.1、26n 38.9；我们 ORT 1 线程是 68.4 和 60.1。同线程归一后，官方比我们快 1.94 倍和 1.54 倍。11n 多出来的 25% 很有意思 —— 说明官方那份老图里的 DFL 子图没被很好融合，而我们这份是融合了的。所以这个差距不能直接读成"我们的机器慢 2 倍"。
>
> 沉淀成三条：口径先行、比值优于绝对值、差异超过 10% 才作结论。

**追问**
- *问：既然绝对值不可比，为什么还报毫秒数？* → 报是为了给出量级感；所有结论都建立在同会话内的比值上。
