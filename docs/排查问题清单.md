# 排查问题清单

> 本文收**正确性、环境、数据、方法论**四类排查结论。
> 精度实验的"对比了哪些、排除了哪些假设"见 `docs/条码实验记录.md` §1 与 §1.1，
> 本文不重复。

分类逻辑：**A 类会让实验结论直接作废**（必须最先修），B 类决定"这份数据值不值得
相信"，C 类是可复现性的坑，D 类是"数字对不对"的判据本身，E 类是我自己犯过的
过程错误。

## A. 会让结论作废的正确性 bug

| # | 问题 | 症状 | 根因 | 修复 |
|---|---|---|---|---|
| A1 | **BN 动量失真** | 验证/测试准确率恒为 **77.02%**，恰好等于"全猜多数类 EAN13"的 754/979 | torchvision 的 MobileNetV3 沿用 TF 配方 `momentum=0.01`；本项目 batch 32 时一轮只有 143 步，running 统计量残留约 24% 的初始化值，46 层 BN 串联放大 → 权重是好的，坏的是 eval 时喂进去的归一化参数 | 统一成 0.1（`5dfb1fe`）。排查全文见 `docs/BN统计量排查.md`（`1e4d870`） |
| A2 | **DML 检查点无法加载** | 10 轮全部跑完，最后加载最佳模型时 `UnpicklingError`，results/曲线/报告全部丢失 | DirectML 张量被序列化成 `_rebuild_device_tensor_from_numpy` 重建记录，加载端 `weights_only=True` 不接受 | 保存前一律搬 CPU（`13acbd7`） |
| A3 | Top-K 评估越界 | 类别数 < 5 时 `topk(5)` 直接报错（条码只有 2 类） | 硬编码 k=5 | `fcb8203` |
| A4 | 显式 `--save_path` 被覆盖 | 产物写到默认目录，两次实验互相覆盖 | `model_init` 里重新生成了 save_path | `45d67af` |
| A5 | MACs / 延迟报告互相覆盖 | 第二次实验后第一次的复杂度记录消失，A/B 对比缺一列 | 报告写在 `save_path/..`（同模型共用） | `4ea94db` |
| A6 | 延迟测试写死 3 通道 | 灰度模型 `RuntimeError`：输入 `[1,1,128,128]` vs 权重 `[16,1,3,3]` | 输入张量硬编码 3 通道 | `348cf8f` |
| A7 | `BarcodeDataset` 6 处缺陷 | 预处理/标签映射/异常样本处理不一致 | 单文件 693 行、职责混杂 | 重写（`1acd9b5`）+ 15 项验收测试（`bd102ca`） |
| A8 | 类名改名后调用方未同步 | `train.py` 的 `trainer` → `Trainer` 后 6 处调用报错 | 改名没有全局搜索 | `e243c62` |

**A 类的教训**：这些 bug 有一条共同特征——**不是"跑不起来"，而是"跑起来了但数字是假的"**。
A1 尤其典型：损失正常下降、训练准确率正常、验证准确率一字不动。所以训练框架里
`validation_looks_frozen()` 这个"连续两轮验证准确率完全相同就告警"的钩子是必要的，
它不是防呆，是防 A1 这类事故。

## B. 数据质量与划分审查（Phase 2 诊断）

| # | 审查项 | 方法 | 结论 |
|---|---|---|---|
| B1 | 数据泄漏 | 按源图键分组（6073 组），检查跨 split | **0 组**，无泄漏 |
| B2 | 标签噪声 | 6527 条人工审计 + zxing 交叉解码 | 可疑 **4/6527 = 0.06%**；`label_name == original_type` 全部成立 |
| B3 | 三个 split 是否可比 | 宽高分布统计 | 宽度均值 531.9 / 528.2 / 528.7（差 <2%），可比 |
| B4 | 模型是不是只学了尺寸捷径 | 只用 log(w/h) 做逻辑回归 | majority 76.92% → 阈值法 90.40% → 线性 91.42%；CNN 98.88% → **像素网多贡献 7.46 pt** |
| B5 | 解码器能不能替代分类器 | zxing-cpp 解码结果直接映射成类别 | **85.50%**，比 CNN 低 13.4 pt（且小类覆盖率只有 37%~38%） |
| B6 | 错误是不是都因为"图太糊解不出" | 按可解码性分解 CNN 错误 | **反了**：可解码样本 98.70%（9 错）、不可解码 99.30%（2 错） |
| B7 | 同一源图多区域会不会让错误聚集 | 检查错误样本的源图 | #946/#947/#948 同来自 `Special_0329`，**三个区域全错** → 按源图分组切分才能避免指标虚高 |
| B8 | ISBN 样本是否标注错误 | 交叉解码 | #961/#962 解码为 Code128 且与标签一致 → **标注没错**，是模型判错了外观歧义样本 |

## C. 环境与工具链陷阱

| # | 陷阱 | 表现 | 应对 |
|---|---|---|---|
| C1 | PowerShell `*>` 重定向写 **UTF-16LE** | Python 按 utf-8 读日志 → `UnicodeDecodeError: 0xff` | 先看 BOM `ff fe`，再 `.decode("utf-16")` |
| C2 | `Out-File -Encoding utf8` **带 BOM** | commit message 首字符变成 BOM（`﻿docs(bn):`），git 记录脏 | `[System.IO.File]::WriteAllText` + `UTF8Encoding($false)`，再 `git commit -F` |
| C3 | PowerShell here-string 吞引号 | 内嵌 Python 的三引号被吃 → `SyntaxError: unterminated triple-quoted string`；`$` 会被插值 | 复杂脚本一律写成 `.py` 文件再执行，不走 heredoc |
| C4 | 沙箱禁止写 workspace 之外 | 默认 `save_path`（`saved_models/...` 指向外部）被拒 | 每次显式 `--save_path .tmp_tests\<name>` |
| C5 | 沙箱下多进程受限 | DataLoader 起子进程失败 | 一律 `--num_workers 0` |
| C6 | **DML 比 CPU 慢** | MobileNetV3@128：0.66 s/批（DML）vs 0.22 s/批（CPU）；ResNet-50@224 直接失败 | 基线迭代用 CPU；DML 只做等价性验证，指标一致 |
| C7 | torchvision 内省陷阱 | `InvertedResidual` 没有 `use_se` 属性；`torch.nn.modules.se` 不存在；**步长不在 `block.block[0]`**（1×1 扩张卷积永远 stride 1），而在深度可分离卷积上 | 取"块内所有卷积的最大步长"；SE 用类名判断。踩坑后果：我把累计下采样算成 2 倍（真实是 32 倍） |
| C8 | thop 的噪声与单位 | 每次 profile 打印十几行 `[INFO] Register ...`；返回的是 **MACs 不是 FLOPs**（1 MAC ≈ 2 FLOPs） | 过滤日志；报告里明确写"MACs" |
| C9 | 检查点体积 | 16.2 MB/份，10 轮全留约 170 MB/run，六组实验 652 MB | 只留 `model_epoch_<best>.pth` + `model_last.pth`，降到 246 MB |

## D. 方法论与统计纪律

| # | 问题 | 教训 |
|---|---|---|
| D1 | **单 seed 筛查会骗人** | Label Smoothing 的 seed 0 是 99.59%（看着 +0.20 pt），补 seed 1/2 后变成 99.18 ± 0.37，配对 t=1.52 不显著。"看起来有效"的是噪声 |
| D2 | 判据 | 一律**同 seed 配对比较**：n=3 时配对 t 需 > **4.303**（p<0.05） |
| D3 | **MDE 要先算** | 128 输入 3 seed 标准差 0.11 → 最小可检测效应约 **0.5 pt**。小于它的差异不该花时间追 |
| D4 | 加轮数不是免费的 | 20 轮与 10 轮测试指标完全相同，且第 20 轮 val 崩到 94.48%（loss 0.2618）→ 10 轮够用 |
| D5 | **"顽固样本 = 不可约"这种估上限的方法不成立** | 三个配置都错的 3 个样本，S16 一上来就修好了 2 个。错误集合随架构与 seed 漂移 |
| D6 | 小训练集会毁掉统计功效 | split 反转后配对标准差从 ±0.10 涨到 ±1.03，MDE 从 0.5 pt 升到 **2.57 pt**——真实效应只有 0.5~0.8 pt，于是检不出来 |

## E. 我自己犯的过程错误（记下来避免再犯）

| # | 错误 | 后果 | 规则 |
|---|---|---|---|
| E1 | `edit` 工具改文件时把函数体/文档字符串删掉 | 先后弄坏 `_first_conv_path`、`main()`、一处 `save_model` 行（被拼到下一行） | **每次改完立刻读回或跑测试**，不靠"应该改对了" |
| E2 | heredoc 里塞复杂 Python | 引号/三引号被 PowerShell 吃掉，报错信息还指向错误的行号 | C3：写文件 |
| E3 | **错误架构能静默加载** | `error_audit.py` 硬编码 `MobileNetV3-Large`；S16 的参数形状与原版**完全相同**，`load_state_dict` 不报错，审计出来的错误集合会完全跑偏 | 架构名必须从实验日志里读，不能靠默认值 |
| E4 | 自检输出里"整列都一样"没起疑 | 打印各 block 的 stride 时整列都是 1，累计倍数算成 2 倍，当时没怀疑直接往下写 | **凡是自检表里出现"某列全相同"都要先怀疑采集方式**（E4 与 C7 是同一件事的两面） |

## 与主结论的关系

A1、A2 决定了**后面所有数字可不可信**：A1 不修，后面的 98.88%、99.39% 全是假的
（会一直是 77.02% 的多数类基线）；A2 不修，DML 上的实验连产物都留不下来。

B 类决定了**这份数据值不值得解读**：0 泄漏 + 0.06% 标签噪声，是后面敢用 979 张
测试集下结论的前提。

D 类决定了**0.5 pt 这种量级的差异能不能下判断**：正是 D1/D3 的教训，才让
Label Smoothing、Focal Loss、S16 这三个"看起来有提升"的方案都被正确否决。
